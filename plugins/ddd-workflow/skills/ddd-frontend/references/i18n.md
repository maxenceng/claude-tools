# i18n

Every word the client itself puts on screen comes from a locale file, through `t()`. The
template speaks English and French from the first screen, so the second language is never
a retrofit through every component.

The library is `react-i18next` over `i18next`, both pinned exactly. It gives typed keys
from plain JSON with no extraction step, namespaces that map one-to-one onto bounded
contexts, and a `useTranslation` hook that needs no provider of its own.

## Setup

```ts
// src/i18n/i18n.ts
export const DEFAULT_LANGUAGE = 'en'
export const SUPPORTED_LANGUAGES = ['en', 'fr'] as const
export type Language = (typeof SUPPORTED_LANGUAGES)[number]

/** One namespace per bounded context, plus `common` for the application shell. */
export const resources = {
  en: { common: enCommon, training: enTraining },
  fr: { common: frCommon, training: frTraining },
} as const
...
i18n.on('languageChanged', (language) => {
  document.documentElement.lang = language
})

void i18n.use(initReactI18next).init({
  resources,
  lng: pickLanguage(navigator.language),
  fallbackLng: DEFAULT_LANGUAGE,
  supportedLngs: SUPPORTED_LANGUAGES,
  defaultNS: 'common',
  ns: Object.keys(resources.en),
  // Resources are bundled, so initialisation completes before the first render.
  initAsync: false,
  // React escapes what it renders; escaping here too would double-escape.
  interpolation: { escapeValue: false },
  returnNull: false,
})
```

- **Bundled, not fetched.** The JSON is imported, so translations are there on the first
  render: no loading flash, no `Suspense`, and `initAsync: false` makes it synchronous.
  When the locales grow large enough to matter, lazy-loading a namespace is a later
  decision with its own ADR.
- **The language is picked once,** from the browser: `pickLanguage('fr-CA')` is `fr`, and
  anything the application does not speak is `en`. There is no detector plugin and no
  switcher yet; adding a switcher means calling `i18n.changeLanguage`, nothing more.
- **`<html lang>` follows the language.** Screen readers choose their voice and
  pronunciation from it; French read with English rules is unintelligible. The
  `languageChanged` listener keeps it in step, and the French screen test asserts it.
- **`escapeValue: false`** because React escapes every string it renders. Escaping in
  i18next too would show `&amp;` to the user.
- `main.tsx` imports `./i18n/i18n` once, before anything renders; so does the test setup.

## Typed keys

```ts
// src/i18n/i18next.d.ts
declare module 'i18next' {
  interface CustomTypeOptions {
    defaultNS: 'common'
    resources: (typeof resources)['en']
    returnNull: false
  }
}
```

The English resources are the type of every key. `useTranslation('training')` gives a `t`
that accepts only `training`'s keys, so a typo, a removed key or a key from another
namespace fails `tsc` — the same way a stale API field does. English is the source of the
types; the parity test (below) makes French follow it.

## One namespace per bounded context

```tsx
// src/training/CoursePopularity.tsx
const { t } = useTranslation('training')
```

A context's copy lives in `locales/<language>/<context>.json` and is read through
`useTranslation('<context>')`. `common` holds the application shell's words (`App.tsx`'s
title) and nothing a context owns. The split mirrors the folders: a context's words move or
disappear with the context, and two contexts never fight over a key.

`app.title` is `"app"` in both languages: it is the template's project-name placeholder,
renamed with the project, not translated.

## Keys

```json
{
  "popularity": {
    "heading": "Course popularity",
    "titleLabel": "Course title",
    "lookUp": "Look up",
    "lookingUp": "Looking up…",
    "notFound": "No popularity yet for this course.",
    "popularityOf": "popularity of {{title}}",
    "unreachable": "The server could not be reached; try again.",
    "retry": "Retry"
  }
}
```

That is `src/i18n/locales/en/training.json` in full.

- **A key names what the text is for,** grouped by screen (`popularity.notFound`), not what
  it says (`noPopularityYetForThisCourse`). The wording can then change without renaming
  the key in every file and every language.
- **One key per message,** even when two read the same today. "Retry" on two screens is
  two keys; the second language may need them to differ.
- **Values are interpolated, never concatenated.** `t('popularity.popularityOf', { title })`
  lets French put `{{title}}` where French grammar wants it; `t('popularityOf') + title`
  fixes the English word order into every language. The copy rule catches the `+` form
  when either side is a literal.
- **The ProblemDetail's `detail` is not a key.** It is the server's own sentence, shown as
  sent, in whatever language the server wrote it. Only the client's own words are
  translated — including the fallback for a request nothing answered
  (`popularity.unreachable`), which the client writes because there is no `detail`.

Plurals use i18next's suffixed keys (`count_one`, `count_other`) with a `count` value. The
template has no plural yet, and the parity test compares key sets exactly, so a language
whose plural rules need a different set of suffixes than English will need the test
adjusted — check it on the first plural.

A key added to `en` and forgotten in `fr` would otherwise fall back to English silently —
`fallbackLng` hides it from everyone but a French reader. The test reads `resources`, so a
new namespace is covered as soon as it is registered, and the failure names the missing
key. An empty message fails too: it renders as nothing, which looks like a layout bug.

## Adding a context's namespace

1. Write `locales/en/<context>.json` and `locales/fr/<context>.json` with the same keys.
2. Import both in `i18n.ts` and add them under `en` and `fr` in `resources`.
3. `ns: Object.keys(resources.en)` and the typed keys pick it up; nothing else changes.
4. Run `make check`: `tsc` checks the keys the screen uses, and the parity test checks the
   two files against each other.

## Adding a language

1. Write `locales/<language>/<namespace>.json` for every existing namespace.
2. Import them, add the language to `resources`, and add its code to
   `SUPPORTED_LANGUAGES`.
3. Extend the parity test so it compares the new language with English too — it names `fr`
   today — and add a case to `i18n.test.ts` for `pickLanguage`.
4. Add a screen test in the new language, like *speaks French when the language is French*.

## Tests

The setup pins English at load and after every test, so behaviour tests assert English text
and do not depend on the machine's locale (`tests.md`). One test per screen switches
language and finds a control by its translated name, which proves the screen reads its copy
through `t()` in its own namespace. Tests are exempt from the copy rule: their fixture copy
is not the product's.
